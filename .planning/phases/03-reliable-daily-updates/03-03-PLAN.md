<objective>
Make the daily refresh structurally reliable (DAILY-01) and crash-tolerant (DAILY-03), entirely with locally-testable code + workflow files. NO GitHub run happens in this plan — enabling the cron is gated behind the human-verify checkpoint in 03-04.

DAILY-01 — incremental scheduling (mechanism = stale-first, chosen over day-of-week round-robin):
  Rationale: stale-first self-heals. A route that fails or times out today is automatically the stalest tomorrow, so it gets first priority next run — which is exactly what turns "daily" from a 3-day patchwork into reliable convergence (DAILY-UPDATES.md section 1.4 root cause + 3.1 + 4.3). Round-robin cannot react to failures (a route that fails on its assigned weekday waits a full week). Stale-first also reuses the scanned_at signal 03-01 already produced — one source of truth for both freshness display and scheduling.
  Query-count math (DAILY-UPDATES.md measured 10.83 s/query): a per-shard budget of ~400 queries is about 72 min — comfortably under both the 350-min timeout-minutes and the hard 6h GitHub wall. 6 shards x 400 = 2,400 daily queries against the stalest slice; combined with a coarse daily grid (--grid-step) the daily job never approaches the wall. Refine stays weekly-only (bound cost) per CONTEXT discretion.

DAILY-03 — fault tolerance: scan and upload become SEPARATE workflow steps; the upload step uses if: always() so a scan step killed at the timeout still publishes the routes already written to data/scan_*.json (scanner already writes per-route atomically). Add concurrency: so a cron-delayed run (10-30 min common, DAILY-UPDATES.md section 1.4) cannot double-fire.

Purpose: provably-short daily job + partial-publish-on-timeout + weekly safety-net sweep.
Output: scanner flags + budget early-stop, restructured daily scan.yml (dispatch-only), new weekly sweep workflow, offline scanner test.
</objective>
