<objective>
Fix the data-layer root cause of stale freshness (DAILY-02) and lay the data primitive that the daily incremental scheduler (DAILY-01) needs.

Today `db.cheap_flight_rows()` (db.py L97-119) does NOT include `scanned_at` in the row dict. Because the upsert uses `Prefer: resolution=merge-duplicates`, an UPDATE on an existing route-month leaves `scanned_at` frozen at its first-INSERT `default now()`. The column's default only fires on INSERT, never on UPDATE — so an already-known route's timestamp never advances and the site cannot tell the truth about freshness. The fix: thread the scan's `generated_at` (already present in every scan_*.json, scanner.py L512) through `upload.py` into each row's `scanned_at`.

Also add `db.stale_routes()` — a read helper returning route keys ordered oldest-scanned-first. This is the scheduling signal that 03-03's `--stale-first` scanner mode consumes (per DAILY-UPDATES.md §4.3). Building it here, in the local-testable db layer, keeps the scanner plan focused.

Purpose: honest per-route freshness on UPDATE (DAILY-02) + the stale-first ordering primitive (DAILY-01).
Output: db.py (scanned_at in rows + stale_routes helper), upload.py (generated_at threaded), offline tests green.
</objective>
